Token Lifecycle

From login to revocation

Every step the system takes, from the moment a user signs in, through token rotation, to what happens the instant a stolen token is detected.

01 — Authentication
1
Client
POST /api/auth/login
Sends email and password in the request body.
2
Server
Validates credentials and issues both tokens
Verifies the password against the Argon2id hash. Generates a family_id — a UUID that links every token rotation in this session to a single revocable chain.
Access Token JWT · signed with ACCESS_TOKEN_SECRET · 15 min lifetime · returned in response body
Refresh Token 96-byte random value · SHA-256 hash stored in DB · 7 day lifetime · set as httpOnly cookie

What is a family_id? Every login session gets a UUID called a family_id, stored alongside the refresh token in the database. As the token rotates over time, each new token inherits the same family_id. This links the entire chain of rotations. Token A → Token B → Token C — back to the original login event. Its only purpose is revocation: if any token in the chain is misused, the server can find and revoke every other token in that session by querying a single family_id, without touching tokens from other sessions or other devices.

3
Client
Stores each token where it belongs
Access token is held in JavaScript memory only, never written to localStorage or a cookie. It disappears on tab close. Refresh token is an httpOnly cookie set by the server, JavaScript cannot read or access it at all. The browser holds it and sends it automatically on refresh requests.
02 — Making Authenticated Requests
4
Client
Calls any protected endpoint
Attaches Authorization: Bearer <access_token> to the request header. The refresh cookie is not involved here.
5
Server
Validates the JWT signature, no database lookup
Verifies the token's signature and expiry against ACCESS_TOKEN_SECRET. Because the access token is short-lived and self-contained, no database query is needed on every request. Protected route validation stays fast regardless of scale.
03 — Token Rotation (access token expired)
6
Client
POST /api/auth/refresh
Access token has expired. Client calls the refresh endpoint with no request body, the browser includes the httpOnly cookie automatically.
7
Server
Validates the refresh token against the database
SHA-256 hashes the raw cookie value and looks up the hash in the refresh_tokens table. Three checks must all pass: hash exists, is_revoked = false, and expires_at is in the future.
8
Server
Rotates the token and responds
Marks the current refresh token is_revoked = true. Issues a new refresh token under the same family_id and sets it as a new httpOnly cookie. Returns a fresh access token in the response body. The old token is now permanently dead.
04 — Theft Scenario: Reuse Detected
!
Attacker
Replays an old, already-rotated token
A refresh token that was previously rotated (and therefore revoked) is sent to POST /api/auth/refresh. This is the signature of a stolen token being replayed after the legitimate client already rotated past it.
!
Server
Detects reuse and destroys the entire family
The hash exists in the database but is_revoked = true. A legitimate client never sends a revoked token. The system treats this as a confirmed breach. Every token row sharing the same family_id is immediately revoked, every device using any token from this login session is logged out. Returns 401 TOKEN_REUSED.
05 — Logout
9
Client
POST /api/auth/logout
User signs out of the current session.
10
Server
Revokes this session only
Marks the current refresh token as revoked and clears the cookie. Only this session is terminated. Other devices signed in under different token families are completely unaffected and remain active.
Philosophy

Every decision has a reason

Auth is not a feature, it is the foundation every other feature stands on. The decisions below are not conventions adopted without thought.

🔐

Access tokens live in memory only

The access token is returned in the response body and stored in application memory, never in localStorage or a cookie. localStorage is readable by any JavaScript on the page, including injected scripts. A memory-only token disappears on tab close and is never reachable from the document.

🍪

Refresh token is httpOnly cookie

The refresh token lives in a cookie marked httpOnly, Secure, and scoped to path: /api/auth. JavaScript cannot read it. The browser sends it automatically on refresh requests only. Even a complete XSS attack cannot extract it.

🔄

Tokens rotate on every use

Each successful refresh issues a new refresh token and immediately marks the old one as revoked in the database. A refresh token is single-use by design. This is not optional behaviour, it is enforced at the database layer, not in application logic alone.

🚨

Reuse means breach, act accordingly

If a refresh token that was already rotated is used again, the system treats it as evidence of theft. Every token in that entire family is revoked immediately, logging out all devices for that user. A legitimate client never sends a revoked token.

🔒

Passwords hashed with Argon2id

Argon2id is the winner of the 2015 Password Hashing Competition and the current OWASP recommendation. It is memory-hard, meaning brute-force attacks require significant RAM, not just CPU, per attempt. Hashing happens before any database write, including the temporary pending registration table.

🧱

Strict provider separation

An account created with Google cannot log in with a password, and vice versa. The API returns a machine-readable error code on the attempt, OAUTH_ACCOUNT or ACCOUNT_USES_PASSWORD, so the frontend can route the user correctly instead of showing a generic failure.

Architecture

The dual-token system

Two tokens, two lifetimes, two storage locations. Neither one alone is enough to authenticate a request. ACCESS AND REFRESH TOKEN

Raw tokens are never stored. The server stores only a SHA-256 hash of each refresh token. A database breach exposes hashes, not valid tokens. The raw token only exists in transit and in the client's httpOnly cookie.

Three separate signing secrets

Access tokens, refresh tokens, and password reset tokens each use a distinct JWT secret. A leaked reset token cannot be used as an access token, and rotating one secret does not invalidate the others.

SecretSignsExpiry
ACCESS_TOKEN_SECRETJWT access tokens, contains user ID and role in payload15 minutes
REFRESH_TOKEN_SECRETRefresh token metadata, raw token stored only in cookie7 days
PASSWORD_RESET_SECRETSingle-use password reset link tokens15 minutes
Token Family System

Theft detection that acts.

Most systems check if a token is valid. This one also checks if it has already been used, and responds to reuse as the security event it actually is.

1

Login creates a family

A new random family_id is generated per login session. Every refresh token issued in that session carries the same family ID. This links all token rotations from one login to a single revocable chain.

2

Refresh rotates the token

On a valid refresh request, the current token is marked is_revoked = true in the database. A new token is issued under the same family_id. The old token is now dead, it will never work again.

3

Normal use, client always has the latest token

A client that rotates properly always has the current valid token. There is no race condition in normal usage because each response includes the next token before the client needs it.

4

Reuse detected, family destroyed

If a token that was already rotated (revoked) is presented again, it means one of two things: a bug in the client, or theft. The system assumes theft. All tokens in that family are revoked, every device that was authenticated using that login session is logged out immediately. The response is 401 TOKEN_REUSED.

Family ABC, normal rotation Login Token-1 (active, family: ABC) Refresh ──────▶ Token-1 revoked → Token-2 issued (family: ABC) Refresh ──────▶ Token-2 revoked → Token-3 issued (family: ABC) Logout ──────▶ Token-3 revoked ─────────────────────────────────────────────────────────────── Family XYZ, reuse detected Login Token-A (active, family: XYZ) Refresh ──────▶ Token-A revoked → Token-B issued (family: XYZ) Attacker presents Token-A again (already revoked) ──────▶ REUSE DETECTED, entire family XYZ revoked Token-B also invalidated. User must log in again. Response: 401 TOKEN_REUSED

Endpoints

All endpoints live under /api/auth. Every response follows the same envelope: success, message, and where applicable data.

// Success
{ "success": true, "message": "...", "data": { } }

// Error
{ "success": false, "message": "Human readable message", "code": "MACHINE_CODE" }
POST /api/auth/register

Creates a new account. Behaviour controlled by the REQUIRE_EMAIL_VERIFICATION environment flag.

Request body

{
  "display_name": "Ada Okafor",
  "email":        "ada@example.com",
  "password":     "StrongPass1!"
}

Password must be at least 8 characters, include one uppercase letter, one number, and one special character.

Response, verification disabled

{
  "success": true,
  "data": {
    "user": { "id": "uuid", "email": "ada@example.com", "display_name": "Ada Okafor", "role": "user" },
    "accessToken": "eyJ...",
    "requiresVerification": false
  }
}
// refresh token set as httpOnly cookie named refresh_token

Response, verification enabled

{
  "success": true,
  "data": { "pendingId": 42, "requiresVerification": true }
}
// OTP sent to the provided email. Store pendingId for the verify step.
409EMAIL_EXISTS 400VALIDATION_ERROR
POST /api/auth/verify-otp

Completes registration when email verification is enabled. The user account is created at this point, not during registration.

Request body

{ "pendingId": 42, "otp": "183920" }

Maximum 5 failed attempts. On the 5th failure the pending registration is deleted and the user must start over.

Response

{
  "success": true,
  "data": { "user": { ... }, "accessToken": "eyJ..." }
}
400PENDING_NOT_FOUND 400OTP_EXPIRED 400INVALID_OTP 429OTP_ATTEMPTS_EXCEEDED
POST /api/auth/resend-otp

Generates a fresh 6-digit OTP and resets the attempt counter for an existing pending registration.

{ "pendingId": 42 }
400PENDING_NOT_FOUND
POST /api/auth/login

Authenticates an existing local account. Creates a new token family and returns an access token in the body and refresh token as a cookie.

{ "email": "ada@example.com", "password": "StrongPass1!" }

Both unknown email and wrong password return INVALID_CREDENTIALS with the same message. This prevents email enumeration, an attacker cannot tell whether an account exists from the response.

401INVALID_CREDENTIALS 401OAUTH_ACCOUNT
POST /api/auth/refresh

Issues a new access token using the refresh token from the httpOnly cookie. No request body required, the cookie is sent automatically. The old refresh token is revoked and a new one is issued in a fresh cookie.

// No request body
// curl --cookie "..." https://your-api/api/auth/refresh -X POST

{ "success": true, "data": { "accessToken": "eyJ..." } }
401NO_TOKEN 401INVALID_TOKEN 401TOKEN_EXPIRED 401TOKEN_REUSED
POST /api/auth/logout

Revokes the current refresh token and clears the cookie. Always returns success, a missing or already-invalid cookie is handled gracefully rather than throwing an error.

{ "success": true, "message": "Logged out successfully" }
GET /api/auth/me

Returns the currently authenticated user. Requires a valid access token in the Authorization: Bearer <token> header. Intended for session verification on app load.

{
  "success": true,
  "data": {
    "user": { "id": "uuid", "email": "ada@example.com", "display_name": "Ada Okafor", "role": "user", "is_verified": true }
  }
}
POST /api/auth/forgot-password

Sends a password reset link to the given email. Always returns success regardless of whether the account exists, to prevent email enumeration.

{ "email": "ada@example.com" }

The reset link expires in 15 minutes. Each request generates a new token and invalidates the previous one.

POST /api/auth/reset-password

Resets the user's password using the token from the email link. On success, all existing sessions for the user are revoked across all devices.

{ "token": "raw-token-from-link", "password": "NewPass1!" }

The token is marked used before the password is updated in the database. This eliminates a race condition where two simultaneous reset requests with the same token could both succeed.

400INVALID_RESET_TOKEN 400RESET_TOKEN_USED 400RESET_TOKEN_EXPIRED
POST /api/auth/google

Completes Google sign-in or sign-up. The frontend initiates the flow by redirecting to Google's consent screen. Google redirects back with a one-time code. Extract it and send it here immediately, it expires within seconds.

{ "code": "4/0Adeu5B..." }
{
  "success": true,
  "data": {
    "user": { ... },
    "accessToken": "eyJ...",
    "isNewUser": false
  }
}

isNewUser: true on first sign-in, use this to redirect to onboarding. Google's own tokens are exchanged and discarded server-side, never stored.
